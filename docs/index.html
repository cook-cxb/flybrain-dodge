Fly Dodge

A small browser game where a simulated fly dodges falling obstacles, steered by a network wired from real synapse counts in the male fruit fly central nervous system connectome.

The project asks one question: what happens when you drive a virtual fly with the wiring of a real fly's brain and nervous system instead of hand-written dodge rules? To get there it needed four things, and each one is documented here:

What this is not

It is not a validated model of how a fly escapes a threat. The synapse counts are real. The step from "these descending neurons are active" to "the fly moves left" is my own modelling choice, and the section Real, assumed, unverified lists every such choice. Treat the game as an exploration tool, not as a biological result.

How it works at a glance

  1. Choose the eyes. Four looming-detector cell types (LPLC2, LC4, LC6, LPLC1), 569 neurons in total, are the fly's only sensors.
  2. Find what they connect to. The export script follows their synapses to descending neurons, both directly and through one interneuron, and groups neurons by cell type and body side.
  3. Write the circuit. 8 sensor nodes, 40 interneuron nodes, 40 descending-neuron nodes and 482 weighted connections go into one JSON file.
  4. Run it. Each falling obstacle produces a looming signal for the left or right eye. The network turns it into activity in left-side and right-side descending neurons. A simple rule turns that activity into movement.

Quick start

Path A: just see the game

  1. Open game/fly_dodge.html in Chrome, Firefox or Edge. It needs no internet.
  2. Click Choose file and pick tests/STANDIN_not_real_circuit.json, or your own flybrain_circuit.json if you have already made one.
  3. Click in the arena to drop obstacles. Hold the button before releasing to make a bigger one.
The stand-in file is not real data

It is a made-up circuit that only borrows some numbers from the real report, so the game has something to run on. Use it to try the controls, never to draw conclusions about flies.

Path B: the full pipeline on the real dataset

  1. Make a Python environment (needed on Arch Linux, see Setting up Python): 
    bash scripts/00_setup_venv.sh
source ~/flybrain-venv/bin/activate
  2. Download the three tables (about 1.1 GB) into a working folder: 
    mkdir -p ~/malecns && cd ~/malecns
bash /path/to/flybrain-dodge/scripts/01_download.sh
  3. Inspect them (optional but recommended, prints schemas and cell-type counts): 
    python /path/to/flybrain-dodge/scripts/02_inspect_schema.py | tee inspect_output.txt
  4. Build the circuit (a few minutes; needs roughly 4 to 5 GB of free RAM): 
    python /path/to/flybrain-dodge/scripts/03_export_circuit.py | tee report.txt
    This writes flybrain_circuit.json into the current folder.
  5. Play. Either open the game and choose the JSON file, or serve both from one folder so it loads automatically: 
    cp flybrain_circuit.json /path/to/flybrain-dodge/game/
cd /path/to/flybrain-dodge/game && python -m http.server 8000
# then open http://localhost:8000/fly_dodge.html
No 1 GB download?

To try the scripts without the real data, run python tests/make_synthetic_feather.py demo_data, then cd demo_data and run scripts 02 and 03 from there. The content is random and not biological, but the file formats and column names match.

The male CNS dataset

The data comes from the MaleCNS connectome, an electron-microscopy reconstruction of the central nervous system (brain and ventral nerve cord) of a male Drosophila melanogaster. Every neuron was traced and every synapse located, so the result is a wiring diagram: which neuron connects to which, and through how many synapses. This project uses release male-cns:v1.0.

How big is the picture data?

The page shows the EM volume as (94088, 78317, 134576, 1) voxels at 8 nm, one byte per voxel. Multiplying that out gives about 1015 bytes, roughly one petabyte for the uncompressed bounding box. The file names contain minconf-0.5. I read this as a minimum synapse-confidence cut-off of 0.5, but the page does not spell it out, so check the dataset documentation before relying on that reading.

Memory

The game itself needs very little. The only memory-hungry step is the export script, which reads a 152-million-row table in chunks of 10 million rows and keeps only the rows it needs. Budget roughly 4 to 5 GB of free RAM for it (my estimate; on a 16 GB laptop with the desktop running this should fit). If it gets killed, see Troubleshooting.

Gotchas found while exploring

  • Many neurons have no superclass. 44,877 of 211,577 have a blank superclass, and some descending neurons have a blank type (4 of them in the type list). The export script labels blank types unnamed and never lets them into the circuit.
  • Some types are compound. One descending-neuron type appears as DNp51,DNpe019 (4 neurons). It is treated as its own type.
  • Side is a column, not a naming convention. The script builds node names as type_side (for example LPLC2_L) from somaSide, and uses ? when the side is blank.
  • Newer pandas hides text columns from a dtype check. See Mistakes found along the way.

Correction to an earlier statement

Earlier in the project I said I was confident that LPLC2, LC4 and LC6 all drive the giant fiber escape. For LC6 that was too strong. A published study (see Sources) describes LC6 as a looming-responsive cell type whose activation elicits takeoff, but not a direct input to the giant fiber pathway described by Ache et al. 2019. Whether the male CNS data shows direct LC6 synapses onto DNp01 is a question the data can answer: run scripts/04_input_contributions.py on your circuit file and look at the LC6 column.

Other looming-related types were available but left out. LC16 has 182 neurons and is described alongside LC4, LPLC2 and LC6 as looming-responsive with avoidance behaviour. Adding it is one edit to INPUT_TYPES in the export script. Another type, LPLC4 (97 neurons), also sits among the visual projection neurons and was not used as a sensor; the real report shows it as the highest-ranked interneuron, so it is in the circuit, just not at the input.

The outputs: descending neurons

Descending neurons are the cells whose axons run from the brain down the nerve cord to control the body. The dataset has 1,314 of them in 481 types; the largest types are small (for example DNg08 with 23 neurons and DNpe008 with 19). The named ones this project cares about come in left/right pairs of one neuron each: DNp01 (the giant fiber), DNp02 to DNp07, DNp10, DNp11, DNa02 and DNb01 all have exactly 2 neurons. The export script does not pick descending neurons by name. It picks the 40 with the most synaptic drive from the chosen sensors.

Building the circuit file

scripts/03_export_circuit.py reduces 152 million neuron-to-neuron connections to a circuit of 88 nodes. This section walks through what it does, in order. The settings at the top of the script are the only things you normally edit.

INPUT_TYPES = ['LPLC2', 'LC4', 'LC6', 'LPLC1']   # the sensors
N_INTER = 40     # interneuron nodes kept
N_DN    = 40     # descending-neuron nodes kept
MIN_EDGE = 10    # drop type-to-type edges with fewer total synapses
SIGN = {'acetylcholine': 1, 'gaba': -1, 'glutamate': -1}   # anything else -> 0

Nodes are cell type plus side

A single neuron is too fine-grained for a small game, and a whole cell type ignores left and right. The script's compromise is a node = type + soma side, for example LPLC2_L (94 neurons) or DNp01_R (1 neuron). The edge between two nodes is the sum of synapses over every neuron pair. Node size is kept (n) because it matters when weights are normalised later.

  1. Load and label. Read annotations, drop duplicate IDs, fill blanks (unnamed type, ? side), join consensus_nt from the neurotransmitter table, and build the type_side name for every neuron.
  2. Pick the endpoints. Sensors are all neurons whose type is in INPUT_TYPES (569 neurons). Outputs are all neurons with superclass == "descending_neuron" (1,314).
  3. Scan the weights once. Read the 152-million-row table in 10-million-row chunks. Keep rows that leave a sensor, and rows that arrive at a descending neuron. On the real data this left 505,699 sensor-outgoing edges and 818,956 descending-neuron-incoming edges. Everything else is discarded as it is read, which is why memory stays bounded.
  4. Find the paths. Direct: a sensor synapses straight onto a descending neuron. Two-step: a sensor synapses onto some neuron X, and X synapses onto a descending neuron. X can be any neuron that is not itself a sensor or a descending neuron.
  5. Keep the 40 most important interneuron nodes. Each node X is scored by the geometric mean of what it receives from sensors and what it sends to descending neurons: score = sqrt(in × out). Unnamed nodes are skipped.
  6. Keep the 40 most driven descending-neuron nodes. A node's drive is its direct synapses from sensors plus its synapses from the kept interneurons. Unnamed nodes are skipped.
  7. Write the outputs. Nodes and edges go to flybrain_circuit.json. Edges with fewer than MIN_EDGE = 10 synapses are dropped. A report is printed to the terminal (see the next section).

The sign rule assumption

Each node takes the majority consensus_nt of its neurons. Acetylcholine counts as excitatory (+1), GABA and glutamate as inhibitory (−1), and any other or missing transmitter as 0, meaning the connection has no effect in the game. Glutamate is a simplification: in flies it can act either way depending on the receptor. Of the top 15 interneuron nodes above, 10 are cholinergic, 3 glutamatergic and 2 GABAergic.

What the reduction leaves out

  • Paths longer than two steps, and any interneuron-to-interneuron connection. Only sensor→descending and sensor→X→descending paths exist in the circuit.
  • All but the top 40 interneuron nodes and top 40 descending-neuron nodes. The choice is by synaptic drive, not by what the neurons do.
  • Edges under 10 synapses.
  • Everything inside a node: individual neurons, their positions, and their timing.
Runtime

Reading the weights table dominates: a few minutes, with peak memory around 4 to 5 GB (estimate). The terminal prints a running "millions of rows scanned" counter to stderr while it works; on the author's run it ended at 152M.

Relation to the literature literature

Jang et al. 2023 report that several looming-responsive descending neurons, including the giant fiber, combine information from both eyes even though their dendrites sit on one side, and that contralateral information reaches the giant fiber through a pathway that was unidentified at the time. The mixed two-step numbers above are consistent in spirit with that. I have not checked whether the interneurons in this circuit are that pathway, and this is not evidence for it.

I treat somaSide as the eye side, i.e. a left-soma looming detector is taken to see the left visual field. That is the usual arrangement for these cell types but I did not verify it for each one in this dataset.

The circuit JSON

flybrain_circuit.json is what the game reads: one object with a meta block, a list of nodes and a list of edges. It is on the order of 100 KB (my estimate for 88 nodes and 482 edges; ls -l will tell you). The layout below is schematic: the field names are exact, values marked … or in angle brackets are placeholders.

{
  "meta":  { "dataset": "male-cns v1.0",
             "input_types": ["LPLC2", "LC4", "LC6", "LPLC1"],
             "sign_rule": { "acetylcholine": 1, "gaba": -1, "glutamate": -1 },
             "min_edge": 10 },
  "nodes": [
    { "id": "LPLC2_L", "type": "LPLC2", "side": "L", "layer": "input",
      "n": 94, "nt": "<majority transmitter>", "sign": <+1, -1 or 0> },
    { "id": "LPLC4_R", "type": "LPLC4", "side": "R", "layer": "inter",
      "n": <neurons>, "nt": "acetylcholine", "sign": 1 },
    { "id": "DNp01_R", "type": "DNp01", "side": "R", "layer": "dn",
      "n": 1, "nt": "<…>", "sign": <…>, "subclass": "lt", "exit_nerve": "" }
  ],
  "edges": [
    { "pre": "<node id>", "post": "<node id>",
      "total": <synapses summed over all neuron pairs>,
      "per_post_neuron": <total / n_post>,
      "n_pre": <…>, "n_post": <…> }
  ]
}
FieldMeaning
layerinput (sensor), inter (relay) or dn (descending neuron)
nNumber of neurons in the node
sign+1, −1 or 0 from the node's majority neurotransmitter. The game applies the presynaptic node's sign to each outgoing edge
totalAll synapses from every neuron in pre onto every neuron in post
per_post_neurontotal / n_post. This is the strength the game actually uses: how many synapses an average receiving neuron gets from the whole presynaptic node

Only the sensor→descending, sensor→interneuron and interneuron→descending kinds of edge exist. The game ignores any edge that points at a sensor, and any edge whose endpoints are missing from nodes.

Checking a claim against the file

The JSON is small enough to interrogate directly. scripts/04_input_contributions.py prints, for the strongest descending-neuron nodes, how many direct synapses come from each sensor type:

python scripts/04_input_contributions.py flybrain_circuit.json 12

Use it to check, for example, whether DNp01 receives direct input from LC6 in this dataset, or how large LPLC2's share is compared with LC4's. Remember that edges under 10 synapses were already dropped.

From obstacle to eye signal

The fly has no camera. Each frame, every falling obstacle is turned into a single number per eye that stands for "how strongly is something looming at me on this side". Everything in this section is assumption: the connectome says nothing about how the sensor neurons are driven.

Per obstacle

Let p be the obstacle's centre relative to the fly, v its velocity relative to the fly, r its radius, d = |p| and R = 7 px the fly's radius.

closing speed     c   = −(p·v) / d                      (skip the obstacle if c ≤ 0: it is receding)
time of closest   tca = −(p·v) / |v|²
miss distance     b   = | p + v·tca |
on-course gate    g   = exp( −( b / (1.3·(r+R) + 12) )² )
expansion rate    e   = r·c / (d² + 0.5·r²)             (per second)
bearing           φ   = atan2(px, py)  in degrees, + = right of heading
half-width        α   = asin( min(1, r/d) )
  • Expansion rate e is how quickly the obstacle's angular size grows. The exact figure for a circle is r·c / (d·√(d²−r²)); I soften the denominator so it stays finite when the obstacle is very close.
  • The gate g is 1 for an obstacle heading straight for the fly and falls off for one that will pass wide. It stands in for the collision-course selectivity of looming detectors such as LPLC2, so a ball that will miss does not trigger an escape.

Per eye

s_R(φ) = smoothstep(−25°, +5°, φ) × ( 1 − smoothstep(130°, 170°, φ) )       s_L(φ) = s_R(−φ)
ℓ_eye  = Σ over obstacles  [ mean of s_eye over 5 bearings in φ±α ] × g × e
a_eye  = ℓ² / (ℓ² + ℓ0²)                                                 ℓ0 = looming threshold

Averaging the eye sensitivity across the obstacle's angular width matters for big, close obstacles that fill both eyes. a_eye is a Naka-Rushton saturating curve between 0 and 1; the Looming threshold slider sets ℓ0 (default 0.25 per second). Lower values make the fly react earlier.

How the eye signal reaches the circuit

Every sensor node on the left receives a_left and every sensor node on the right receives a_right, passed through a 20 ms first-order lag. All four sensor types get the same number, because the data does not tell me how their tuning differs. Sensor nodes with unknown side (?) get the average. Obstacles that have already burst are ignored.

Consequence of this choice

Since the four types are fed identically, any difference between them in the game comes purely from their wiring downstream, and silencing a type only removes its wiring's contribution, not a different kind of visual response.

The rate model

Each node has an activity a between 0 and 1, standing for the average firing of its neurons. Sensor nodes are set from the eye signals. Every other node follows the equations below.

weight             w_ij = sign(node i) × per_post_neuron(i → j)                      from the data
drive              x_j  = gain × ( Σ_i w_ij · a_i ) / scale(layer of j)  + noise      noise: Gaussian, σ = 0.04
response           f(x) = x / (1 + x)  if x > 0,  else 0
dynamics           τ · da_j/dt = −a_j + f(x_j)                                        τ = 30 ms, Euler step 1/120 s
  • Why per_post_neuron. If every presynaptic neuron fires at rate a, an average postsynaptic neuron receives per_post_neuron × a synapse-weighted drive. This normalises for how many neurons a node contains, so a big population is not automatically stronger.
  • Why x/(1+x). A rectified saturating curve keeps every node between 0 and 1 no matter how large the synapse counts are.
  • Why noise. It breaks ties. Without it, a perfectly symmetric situation (an obstacle straight overhead) would leave the fly frozen or always choosing the same side. Idle noise is small: in a 10-second test with no obstacles, the fly drifted at most 17 px from home.

Calibration: turning raw synapse counts into sensible activity

Raw counts span orders of magnitude (from the report: tens to thousands). Feeding them straight into f would either saturate everything or silence everything, so at load time the game calibrates three constants from one reference stimulus: all left-side sensors at activity 0.8 and all right-side sensors at 0.

  1. scale(inter) = the median of the positive interneuron drives. A typical driven interneuron then sits at x = 1, half saturation (a = 0.5).
  2. With those interneuron activities, scale(dn) = the median of the positive descending-neuron drives, in the same way.
  3. motor_scale is chosen so that the summed left-side descending activity for this stimulus equals 0.8.

The right-side summed activity under the same stimulus is then a direct measure of how well the circuit separates sides. The game prints it when a file loads: "a strong looming object on the left drives left-side descending neurons to 0.80 and right-side ones to …". A value near 0 means a strongly lateralised circuit; a value near 0.80 means the circuit barely distinguishes left from right. On my made-up stand-in it was 0.53; for the real file, read your own status line.

The three constants are computed once from the unmodified weights and then held fixed, so the controls in the game (silencing, rewiring) change the behaviour rather than silently re-tuning it.

Limits assumption

The node-level model has no time delays beyond the 30 ms lag, no adaptation, and no recurrent or interneuron-to-interneuron connections. It is a feed-forward snapshot of a two-step wiring diagram, not a simulation of neurons.

From neurons to movement

The circuit ends in descending-neuron activity. The dataset cannot tell me what each of these neurons does to a body, so the game uses a single rule for all of them. assumption

S_L = motor_scale × Σ activity of left-side descending nodes       S_R = the same for the right side
T      = S_L + S_R                                                   overall threat
drive  = T / (T + T0)                                                T0 = 0.35
asym   = tanh( κ · (S_L − S_R) / (S_L + S_R + 0.05) )                κ = 10 ("Left/right decisiveness")
sym    = 1 − |asym|
v_x    = vmax · drive · asym                                         (+ = move right)
v_y    = − vmax · retreat · drive · sym                              (− = move down)     retreat = 0.5,  vmax = 560 px/s

In words: activity on the left pushes the fly right, and activity on the right pushes it left; if both sides are active about equally, the fly backs away downwards; if nothing is active, it drifts back home.

The direction rule is a choice, and the literature is not on its side literature

Jang et al. 2023 found that the giant fiber responds to looming about equally wherever in azimuth the stimulus appears, and that several looming-responsive descending neurons integrate both eyes. So real activity of these neurons does not, by itself, encode which way to flee. My rule ("left-side activity means move right") is a stand-in that makes the wiring's left/right structure visible in the game. It is a modelling device, not a claim about how a fly picks its escape direction.

The rule also has an obvious blind spot: vertical avoidance is only "back away when both sides fire", so a fly cannot choose to climb over an obstacle. Section Where to go next discusses what would be needed to change that.

Hits and the "dodged" score

  • Hit: centre distance below r + 7. Counted once per obstacle; the fly is knocked away at 260 units/s and flashes red.

Using the game

The game is a single file, game/fly_dodge.html, with no libraries and no network use. It has two panels: the arena on the left and the fly's circuit on the right.

Loading the circuit

  • Choose file, or drag flybrain_circuit.json onto the box. The file is read in the browser and goes nowhere else.
  • Paste the JSON into the text box if a file picker is unavailable (some embedded viewers block it).

Experiments to try

The controls are there so you can test whether the wiring matters, instead of taking it on faith. Hit and dodge counts are noisy, so run each condition for at least a minute of Rain, press Reset score between conditions, and treat differences of a few counts as noise.

  1. Intact against cut brain. Turn Rain on for 60 s with the defaults, note dodged and hit, reset, tick cut the brain and repeat. The brain-cut fly should be hit far more often. On the stand-in circuit over 90 simulated seconds: intact 12 dodged and 1 hit; brain cut 4 dodged and 8 hits.
  2. Intact against rewired. Repeat with rewire ticked. See the caveat in Results: this gap depends on the decisiveness setting.
  3. Silence one sensor type at a time. Because all sensor types get the same signal, differences between them reveal how much each one's wiring contributes to escape-related descending neurons in your file.
  4. Watch a left drop and a right drop. Drop an obstacle well to the left of the fly, then well to the right, while watching the circuit panel. Which descending nodes light up on which side? Compare SL and SR with the calibration line printed at load.
  5. Head-on drop. Drop directly above the fly. Both eyes see it, SL and SR are close, and noise decides which way it goes; try a few times and see the split.
  6. Turn the knobs. Lower the drop height and raise the looming threshold to make the game hard; raise decisiveness to see how much of the fly's success comes from that one setting.

What to conclude, and what not to

  • The mechanics work. The fly moves away from the side that is looming, is idle when nothing threatens, and does much worse without its eyes or its brain.
  • The intact-versus-rewired gap is modest and knob-dependent. At the default it is 3% versus 12%, but at κ = 8 with strong retreat they are equal (8% each). Mistakes found along the way

These are real problems that came up during the project, kept here because they explain several design decisions.

1. pip refused to install (Arch Linux)

error: externally-managed-environment. The system Python is protected. Fixed with a virtual environment. See Setting up Python.

2. The first cell-type search printed nothing

The first inspection script ran to the end but its "candidate cell types" list was empty. I first suspected it had run out of memory. That was wrong: the newer pandas stores text as a dedicated str dtype, and my check looked for object columns, so it skipped every text column. The fix was to select the columns by name (type, superclass) instead of by dtype. The packaged 02_inspect_schema.py already does this.

3. An overstatement about LC6

I said I was confident LC6 drives the giant fiber. Later checking of the literature showed LC6 is looming-responsive and evokes takeoff, but is reported not to be a direct giant-fiber input. Corrected in Choosing the cells, with a script to check it in the data.

4. A shuffle control that did not shuffle the structure

The first version of the control permuted the weights among the connections that already existed. Since which neurons connect to which is exactly what carries left/right structure, the fly still lateralised correctly and even hit less often than the intact one. It was not a control. It was replaced by rewiring: each connection keeps its source and strength but gets another connection's target. That produced the expected ordering (intact better than rewired better than no brain).

5. Floor clutter made the intact fly worse than no brain

Obstacles originally bounced and rolled after landing. In 90 s of rain the intact fly was hit 14 times against 8 for the brain-cut fly. Tracing the hits showed 33 of the 54 total came from balls lying or rolling on the floor: the retreat rule sent the fly downward into them, and, most likely, the floor lies largely outside the eye fields (I inferred this from the geometry, not from a separate experiment). Making obstacles burst on first contact fixed it (intact: 1 hit in 90 s).

6. Too many head-on hits, then a knob that flatters everything

With decisiveness 4, all 23 hits (out of 112 drops) were drops within 10 units of straight overhead (10 at offset 0 and 13 at offset −10 in the test grid): both eyes were stimulated almost equally and the sidestep was weak. At 10 only 3 hits remain (1 and 2 at the same offsets). It also made the rewired control look better (see Results), so it is a slider rather than a hidden constant.

7. Small tooling slips

A shell brace-expansion ({a,b,c}) did not work in /bin/sh and created a literal folder; corrected by running under bash. Nothing in the deliverables depends on it.

Sensing: the same eye math, now in full 3D

The 2D game measured a bearing in degrees around a fixed frame. The 3D game measures it relative to the fly's actual facing, using vector dot products instead of a fixed angle, so the same left/right split now depends on which way the fly is pointed:

p = obstacle.pos − fly.pos            (as before: closing speed, time-to-closest-approach, miss distance, gate g, expansion rate e — unchanged formulas, see From obstacle to eye signal)
azimuth  φ = atan2( p·right, p·fwd )        + = right of the fly's nose
elevation ε = atan2( p·up, horizontal distance )    + = above the fly

The same eyeSens(φ) ramp from the 2D game turns azimuth into a left/right split. Elevation feeds a new, separate quantity:

vBias = (Σ sign(ε) · strength) / (Σ strength)      strength = gate × expansion rate, summed over obstacles

vBias runs from −1 (threats mostly below) to +1 (mostly above). I checked its sign in isolation before wiring it in: a closing obstacle placed above the fly gives vBias = 1, level gives 0, below gives −1.

Motor: yaw from the data, pitch from geometry

T = S_L + S_R                                    drive = T / (T + T0)             T0 = 0.4
asym = tanh( κ (S_L−S_R) / (S_L+S_R+0.05) )    κ = 9 default (was 10 in 2D)
yawCmd   = k_yaw · drive · asym                  k_yaw = 1.0
pitchCmd = −k_pitch · drive · vBias              k_pitch = 0.6 default, slider-adjustable

Yaw is the direct 3D equivalent of the 2D sidestep: it comes from S_L and S_R, the same real synapse-weighted descending-neuron activity as everywhere else in this project. Pitch has no connectome basis at all — the tables carry no information about elevation in the visual field, so vBias is pure scene geometry, not neural activity. It's gated by drive (computed from the real brain output) so the fly only dives or climbs when something real is actually threatening it, but the direction of that dive/climb is my invention, not a finding. The game's own on-page notes say this plainly, not just these docs.

When nothing threatens the fly, a gentle, also-assumed autopilot steers it back toward the room's centre and mid-height so it doesn't just fly into a wall — the free-flight equivalent of the 2D game's homing behaviour, needed for playability, not derived from data.

Obstacles

Spawn near the ceiling (Y=152 of a 165-unit-tall room) at a random or clicked X/Z, each with its own small constant sideways drift assigned at spawn (26 / (1 + 0.12r) units/s, so smaller obstacles drift more), and gravity pulling them down. They bounce off the four walls (reversing the relevant drift component) but burst on touching the floor, fading over 0.35 s, exactly like landed obstacles in the 2D game.

Finding the orientation

An OBJ file states no convention for which axis is forward. The raw vertex bounding box gave a first clue: X (wingspan) ranges ±2.75mm, Y (height) 0 to 2.62mm, and Z (length) −2.95mm to +1.64mm — asymmetric, meaning the model isn't centred at its own origin in Z. To find out which end was which, I rendered the raw triangles as orthographic wireframes (top, side, front views) directly from the vertex data, colour-coded by group. That made the shape unambiguous: a round head with legs splayed near the front, tapering to a larger abdomen at the back, wings attached near the shoulder. Head is at +Z, up is +Y, and X is left/right (the model is bilaterally symmetric, so handedness there doesn't visually matter).

This mattered because the game's fly orientation math (above) already treats local +Z as forward and +Y as up — so once the model's own axes were confirmed to mean the same thing, it could be dropped straight into that frame with no extra rotation.

Getting it into the browser

A published page can't fetch outside files — no loading a separate .obj, .mtl or .tif at runtime. Everything had to be preprocessed into something that could be embedded as text in the HTML itself:

  1. Parse the OBJ myself (a few dozen lines of Python) rather than shipping an OBJ-parsing library. For each triangle corner, look up its position and UV coordinate and "unroll" them into flat, non-indexed arrays — simpler than reconstructing an indexed mesh, and small enough at this triangle count (9,774 corners total) not to matter.
  2. Centre and scale. Vertices were in metres (a real fly's actual size, ~5.5 × 2.6 × 4.6mm). Centred on the bounding-box midpoint, then scaled ×2000 so the model's total length comes out to about 9.2 game units — comparable to the old placeholder cone's length of 8, and the reason the fly's collision radius went from 3 to 5.
  3. Skip normals. Rather than compute or ship vertex normals, the browser calls BufferGeometry.computeVertexNormals() once at load time — a standard three.js method, one line, no extra data to embed.
  4. Convert and shrink the textures. TIFF isn't a web format. Both were converted to PNG and downsized to a maximum of 256px on the long edge (554×420 → 256×194 for the body; 652×420 → 256×164 for the wing).
  5. Embed everything as base64. Two float32 position arrays, two UV arrays, two PNGs — all inlined directly in the page's JavaScript as base64 strings, decoded in the browser with atob into Float32Arrays and data-URI textures.

A plain click, with little or no drag, still drops an obstacle — only a real drag (past a 6px threshold) is treated as a look instead.

Switching to Free starts exactly from where the chase camera was looking at that instant (computed from the chase camera's position and look-at target, converted to yaw/pitch), so there's no jump. Arrow keys only act when Free mode is on and the browser's focus isn't inside a text field, slider or other form control — so they don't hijack a slider you're adjusting with the keyboard.

Design choice, not a connectome result: free flight plus a chase-or-manual camera was chosen over the original hover-in-place 2D design specifically because it gives the connectome's real left/right wiring something more natural to do — steering a moving body's turn, rather than pushing a stationary dot sideways.

A paler room

The room's background was originally a dark navy space, unrelated to the rest of this project's colour scheme. It now uses the same background colour as the surrounding page — literally the same CSS custom property, --bg — in both light and dark themes, so the 3D view sits inside the page rather than looking like a separate dark window cut into it. Grid lines and room-edge wireframes were recoloured to stay visible against a pale background (previously they only had to work against near-black); ambient lighting was brightened to match. This is a styling change only — it touches no simulation logic.

Testing the 3D version

The same approach as the 2D game: test the simulation math directly in Node first, then test the page's wiring in a headless browser. Nothing here involves an actual GPU — none was available while building this, so rendering itself (whether the textures map correctly, whether proportions and lighting look right) has never been seen, only reasoned about.

A mistake caught by the test itself

An early version of the camera test "reloaded" the circuit mid-test to get a clean slate, which actually created a brand-new World3D object — while the test's own reference to the world still pointed at the old, now-abandoned one. Every obstacle-count check after that point was silently reading a frozen object that no longer received updates, which surfaced as a crash (reading a property of undefined) a few checks later rather than as an obviously wrong number. The fix needed two things: reopening the loader UI doesn't actually reset the world (so the reload was unnecessary to begin with), and rain mode — left on from an earlier check — needed to be explicitly turned off before counting obstacles deterministically. Left here because it's a good example of why "it crashed later" is often a stale-reference bug two steps earlier, not a bug where the crash happened.

Where to go next

A 3D room — built

This was discussed, then built; see The 3D version for the full writeup. The predictions from the original discussion held up:

  • Memory was not the obstacle. The finished fly_dodge_3d.html is 459 KB, and the 1.1 GB weights file was only ever needed once, offline, to build the small circuit JSON. No measurement of in-browser memory use was possible in this environment (no GPU), but nothing in the design should come close to being a problem on a 16 GB laptop.
  • 3D did not fix the main limit, as predicted. Left/right steering is data-driven, exactly as expected. Climb and dive are a geometric stand-in with no connectome support, exactly as predicted — and with a third axis actually in use, that gap is more visible in the finished game than it was in the 2D one, not less.
  • The retinotopy route was not attempted. Elevation still doesn't come from the data; it comes from where obstacles happen to sit around the fly right now. The syn-points route described below remains open.
  • The design choice was settled: free flight, not hovering-in-place. The fly turns and dives away from threats rather than sidestepping them, which is a better fit for what the real wiring's left/right signal can actually justify.

What wasn't part of the original discussion, and got added while building: a real fly model in place of the placeholder cone (from a user-supplied file, see The 3D fly model), and two camera modes including a free-flying manual camera (see Camera and room).

Still open: elevation from real data

The 12.7 GB syn-points table holds synapse positions. As I understand it, the looming detectors' dendrites are arranged retinotopically in the optic lobe, so synapse positions could in principle give each neuron an approximate look direction. I have not checked that the table supports this, and the mapping would be approximate. It would also mean modelling individual neurons: 569 sensors plus 1,314 descending neurons, and the neuron-level tables the export script filters (505,699 sensor-outgoing rows and 818,956 descending-incoming rows, with direct connections counted in both). That is feasible in a browser only with a compact binary file, and reading syn-points would need batch reading rather than loading it into pandas. This is the one piece of the original 3D discussion that remains exactly where it was.

Smaller steps that need no new data

  • Add LC16 to INPUT_TYPES and compare the resulting circuit.
  • Use script 04 to check the literature claims about LC4, LPLC2 and LC6 against the real synapse counts.
  • Let each sensor type have its own tuning (for example size-sensitive versus speed-sensitive) once you have a reason from the literature.
  • Include three-step paths, or interneuron-to-interneuron edges, and see whether the left/right structure changes.
  • Replace the single motor rule with roles for individual descending neurons taken from published function.

Project log

How the project unfolded, in order.

  1. Sizing the download. The dataset page lists seven tables totalling about 24.1 GB, plus skeletons, a database and image volumes that are not sized. The EM volume shape implies about a petabyte uncompressed (my arithmetic).
  2. The idea. A game in which a blue dot at the bottom dodges obstacles that fall when the user clicks, steered by the male connectome. I explained that the full connectome cannot run in a web page, so the plan became a small subset: sensors, relays and descending neurons, with the real weights.
  3. Choosing the files. Only 1.2 GB of the 24 GB was needed: annotations, neurotransmitters and weights. The three files downloaded fine.
  4. Setting up Python. pip refused on Arch; a virtual environment fixed it.
  5. First look at the tables. Schemas and sample rows appeared. The weights table has 151,856,684 rows. The cell-type search returned nothing because of the pandas string-dtype issue; fixed by selecting columns by name.
  6. Confirming the cell types. Counts for LPLC2 (185), LC4 (126), LPLC1 (134), LC6 (124) and the descending-neuron classes confirmed the plan was feasible.
  7. Building the circuit. The export script ran on the real data, producing 88 nodes and 482 edges and the report reproduced in this documentation. The report showed same-side direct wiring, mixed two-step wiring, and LPLC4 as the top relay.
  8. Designing the game around the data. Because only left/right is in the data, the earlier idea of four movement groups was dropped in favour of the left/right, back-away and homing rule.
  9. Testing and repairing. A stand-in circuit built from the report numbers exposed a broken control, floor clutter and a head-on weakness (all in Mistakes found along the way). The page was tested headlessly and published as a hosted page.
  10. Discussing 3D. Concluded that memory is not the limit and that elevation from data would need the synapse-position tables.
  11. This package. Documentation, scripts, tests, examples and the game bundled for offline use. While preparing it I checked the literature, which led to the LC6 correction and the caveat on the direction rule; and I reproduced the export script from the project record and re-ran it on synthetic data.
  12. Building the 3D version. Free-flight physics and full-3D sensing, reusing the same Brain class unchanged. A stand-in circuit test run again exposed real problems before anything was published: a naive test scenario that reported 0% hits in every condition (a flawed test, not a game bug — fixed by testing against continuous rain instead of staged single drops).
  13. Adding the real fly model. The user supplied fly.rar, a 1999 digitized insect model. Extracting it needed a proper unrar (the free one couldn't handle its solid-archive compression). The model's orientation wasn't stated anywhere in the file, so I rendered orthographic wireframes of the raw geometry to work it out before placing it in the scene. Parsed, centred, scaled and embedded as base64 so the published page needs no external files.
  14. Camera and room styling. Added a Chase/Free camera toggle (arrow keys plus click-drag for the free camera) and repainted the room to match the surrounding page's background instead of a dark, unrelated navy. A stale-object-reference bug in the camera tests themselves (see Testing the 3D version) was caught and fixed before publishing.
  15. This update. Extended this documentation with the 3D version's own sections, and updated the file reference, assumptions table and roadmap to match.
