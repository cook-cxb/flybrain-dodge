The project asks one question: what happens when you drive a virtual fly with the wiring of a real fly's brain and nervous system instead of hand-written dodge rules? The male CNS dataset The data comes from the MaleCNS connectome, an electron-microscopy reconstruction of the central nervous system (brain and ventral nerve cord) of a male Drosophila melanogaster. Every neuron was traced and every synapse located, so the result is a wiring diagram: which neuron connects to which, and through how many synapses. This project uses release male-cns:v1.0. Correction to an earlier statement Earlier in the project I said I was confident that LPLC2, LC4 and LC6 all drive the giant fiber escape. For LC6 that was too strong. A published study (see Sources) describes LC6 as a looming-responsive cell type whose activation elicits takeoff, but not a direct input to the giant fiber pathway described by Ache et al. 2019. Whether the male CNS data shows direct LC6 synapses onto DNp01 is a question the data can answer: run scripts/04_input_contributions.py on your circuit file and look at the LC6 column. Other looming-related types were available but left out. LC16 has 182 neurons and is described alongside LC4, LPLC2 and LC6 as looming-responsive with avoidance behaviour. Adding it is one edit to INPUT_TYPES in the export script. Another type, LPLC4 (97 neurons), also sits among the visual projection neurons and was not used as a sensor; the real report shows it as the highest-ranked interneuron, so it is in the circuit, just not at the input. The outputs: descending neurons Descending neurons are the cells whose axons run from the brain down the nerve cord to control the body. The dataset has 1,314 of them in 481 types; the largest types are small (for example DNg08 with 23 neurons and DNpe008 with 19). The named ones this project cares about come in left/right pairs of one neuron each: DNp01 (the giant fiber), DNp02 to DNp07, DNp10, DNp11, DNa02 and DNb01 all have exactly 2 neurons. The export script does not pick descending neurons by name. It picks the 40 with the most synaptic drive from the chosen sensors. Building the circuit file scripts/03_export_circuit.py reduces 152 million neuron-to-neuron connections to a circuit of 88 nodes. This section walks through what it does, in order. The settings at the top of the script are the only things you normally edit. INPUT_TYPES = ['LPLC2', 'LC4', 'LC6', 'LPLC1'] # the sensors N_INTER = 40 # interneuron nodes kept N_DN = 40 # descending-neuron nodes kept MIN_EDGE = 10 # drop type-to-type edges with fewer total synapses SIGN = {'acetylcholine': 1, 'gaba': -1, 'glutamate': -1} # anything else -> 0 Nodes are cell type plus side A single neuron is too fine-grained for a small game, and a whole cell type ignores left and right. The script's compromise is a node = type + soma side, for example LPLC2_L (94 neurons) or DNp01_R (1 neuron). The edge between two nodes is the sum of synapses over every neuron pair. Node size is kept (n) because it matters when weights are normalised later. Load and label. Read annotations, drop duplicate IDs, fill blanks (unnamed type, ? side), join consensus_nt from the neurotransmitter table, and build the type_side name for every neuron. Pick the endpoints. Sensors are all neurons whose type is in INPUT_TYPES (569 neurons). Outputs are all neurons with superclass == "descending_neuron" (1,314). Scan the weights once. Read the 152-million-row table in 10-million-row chunks. Keep rows that leave a sensor, and rows that arrive at a descending neuron. On the real data this left 505,699 sensor-outgoing edges and 818,956 descending-neuron-incoming edges. Everything else is discarded as it is read, which is why memory stays bounded. Find the paths. Direct: a sensor synapses straight onto a descending neuron. Two-step: a sensor synapses onto some neuron X, and X synapses onto a descending neuron. X can be any neuron that is not itself a sensor or a descending neuron. Keep the 40 most important interneuron nodes. Each node X is scored by the geometric mean of what it receives from sensors and what it sends to descending neurons: score = sqrt(in × out). Unnamed nodes are skipped. Keep the 40 most driven descending-neuron nodes. A node's drive is its direct synapses from sensors plus its synapses from the kept interneurons. Unnamed nodes are skipped. Write the outputs. Nodes and edges go to flybrain_circuit.json. Edges with fewer than MIN_EDGE = 10 synapses are dropped. A report is printed to the terminal (see the next section). The sign rule assumption Each node takes the majority consensus_nt of its neurons. Acetylcholine counts as excitatory (+1), GABA and glutamate as inhibitory (−1), and any other or missing transmitter as 0, meaning the connection has no effect in the game. Glutamate is a simplification: in flies it can act either way depending on the receptor. Of the top 15 interneuron nodes above, 10 are cholinergic, 3 glutamatergic and 2 GABAergic. Checking a claim against the file The JSON is small enough to interrogate directly. scripts/04_input_contributions.py prints, for the strongest descending-neuron nodes, how many direct synapses come from each sensor type: python scripts/04_input_contributions.py flybrain_circuit.json 12 Use it to check, for example, whether DNp01 receives direct input from LC6 in this dataset, or how large LPLC2's share is compared with LC4's. Remember that edges under 10 synapses were already dropped. From obstacle to eye signal The fly has no camera. Each frame, every falling obstacle is turned into a single number per eye that stands for "how strongly is something looming at me on this side". Everything in this section is assumption: the connectome says nothing about how the sensor neurons are driven. φobstacle, fallingleft eye−130° to +5°right eye−5° to +130°heading (up)rear: blind beyond ±170°fly Figure 2. Geometry used to turn an obstacle into eye signals. The fly faces up. The bearing φ is measured clockwise from the heading. Each eye is drawn covering about 135°, with a nominal 10° overlap around straight ahead. Because sensitivity ramps in over 30° (from −25° to +5° for the right eye, mirrored for the left), the effective overlap is wider than the drawn wedges. Per obstacle Let p be the obstacle's centre relative to the fly, v its velocity relative to the fly, r its radius, d = |p| and R = 7 px the fly's radius. closing speed c = −(p·v) / d (skip the obstacle if c ≤ 0: it is receding) time of closest tca = −(p·v) / |v|² miss distance b = | p + v·tca | on-course gate g = exp( −( b / (1.3·(r+R) + 12) )² ) expansion rate e = r·c / (d² + 0.5·r²) (per second) bearing φ = atan2(px, py) in degrees, + = right of heading half-width α = asin( min(1, r/d) ) Expansion rate e is how quickly the obstacle's angular size grows. The exact figure for a circle is r·c / (d·√(d²−r²)); I soften the denominator so it stays finite when the obstacle is very close. The gate g is 1 for an obstacle heading straight for the fly and falls off for one that will pass wide. It stands in for the collision-course selectivity of looming detectors such as LPLC2, so a ball that will miss does not trigger an escape. Per eye s_R(φ) = smoothstep(−25°, +5°, φ) × ( 1 − smoothstep(130°, 170°, φ) ) s_L(φ) = s_R(−φ) ℓ_eye = Σ over obstacles [ mean of s_eye over 5 bearings in φ±α ] × g × e a_eye = ℓ² / (ℓ² + ℓ0²) ℓ0 = looming threshold Averaging the eye sensitivity across the obstacle's angular width matters for big, close obstacles that fill both eyes. a_eye is a Naka-Rushton saturating curve between 0 and 1; the Looming threshold slider sets ℓ0 (default 0.25 per second). Lower values make the fly react earlier. How the eye signal reaches the circuit Every sensor node on the left receives a_left and every sensor node on the right receives a_right, passed through a 20 ms first-order lag. All four sensor types get the same number, because the data does not tell me how their tuning differs. Sensor nodes with unknown side (?) get the average. Obstacles that have already burst are ignored. Consequence of this choice Since the four types are fed identically, any difference between them in the game comes purely from their wiring downstream, and silencing a type only removes its wiring's contribution, not a different kind of visual response. SL and SR feed the motor rule in the next section. Each node has an activity a between 0 and 1, standing for the average firing of its neurons. Sensor nodes are set from the eye signals. Every other node follows the equations below. weight w_ij = sign(node i) × per_post_neuron(i → j) from the data drive x_j = gain × ( Σ_i w_ij · a_i ) / scale(layer of j) + noise noise: Gaussian, σ = 0.04 response f(x) = x / (1 + x) if x > 0, else 0 dynamics τ · da_j/dt = −a_j + f(x_j) τ = 30 ms, Euler step 1/120 s Why per_post_neuron. If every presynaptic neuron fires at rate a, an average postsynaptic neuron receives per_post_neuron × a synapse-weighted drive. This normalises for how many neurons a node contains, so a big population is not automatically stronger. Why x/(1+x). A rectified saturating curve keeps every node between 0 and 1 no matter how large the synapse counts are. Why noise. It breaks ties. Without it, a perfectly symmetric situation (an obstacle straight overhead) would leave the fly frozen or always choosing the same side. Idle noise is small: in a 10-second test with no obstacles, the fly drifted at most 17 px from home. Calibration: turning raw synapse counts into sensible activity Raw counts span orders of magnitude (from the report: tens to thousands). Feeding them straight into f would either saturate everything or silence everything, so at load time the game calibrates three constants from one reference stimulus: all left-side sensors at activity 0.8 and all right-side sensors at 0. scale(inter) = the median of the positive interneuron drives. A typical driven interneuron then sits at x = 1, half saturation (a = 0.5). With those interneuron activities, scale(dn) = the median of the positive descending-neuron drives, in the same way. motor_scale is chosen so that the summed left-side descending activity for this stimulus equals 0.8. The right-side summed activity under the same stimulus is then a direct measure of how well the circuit separates sides. The game prints it when a file loads: "a strong looming object on the left drives left-side descending neurons to 0.80 and right-side ones to …". A value near 0 means a strongly lateralised circuit; a value near 0.80 means the circuit barely distinguishes left from right. On my made-up stand-in it was 0.53; for the real file, read your own status line. The three constants are computed once from the unmodified weights and then held fixed, so the controls in the game (silencing, rewiring) change the behaviour rather than silently re-tuning it. Limits assumption The node-level model has no time delays beyond the 30 ms lag, no adaptation, and no recurrent or interneuron-to-interneuron connections. It is a feed-forward snapshot of a two-step wiring diagram, not a simulation of neurons. From neurons to movement The circuit ends in descending-neuron activity. The dataset cannot tell me what each of these neurons does to a body, so the game uses a single rule for all of them. assumption S_L = motor_scale × Σ activity of left-side descending nodes S_R = the same for the right side T = S_L + S_R overall threat drive = T / (T + T0) T0 = 0.35 asym = tanh( κ · (S_L − S_R) / (S_L + S_R + 0.05) ) κ = 10 ("Left/right decisiveness") sym = 1 − |asym| v_x = vmax · drive · asym (+ = move right) v_y = − vmax · retreat · drive · sym (− = move down) retreat = 0.5, vmax = 560 px/s In words: activity on the left pushes the fly right, and activity on the right pushes it left; if both sides are active about equally, the fly backs away downwards; if nothing is active, it drifts back home. Homing, the only way up When the threat drive is low the fly drifts back to its home point (450, 135) with a speed of min(200, 3 × distance) px/s, scaled by (1 − drive). That is the only source of upward motion. The tables carry no information about where in the visual field a neuron looks, so nothing in the wiring says "an obstacle is below, go up". Body dynamics v ← v + ( v_command + v_home·(1 − drive) − v ) · dt / 0.05 (τ_v = 50 ms) position ← position + v · dt clamped to the arena; altitude limited to 11–430 px The direction rule is a choice, and the literature is not on its side literature Jang et al. 2023 found that the giant fiber responds to looming about equally wherever in azimuth the stimulus appears, and that several looming-responsive descending neurons integrate both eyes. So real activity of these neurons does not, by itself, encode which way to flee. My rule ("left-side activity means move right") is a stand-in that makes the wiring's left/right structure visible in the game. It is a modelling device, not a claim about how a fly picks its escape direction. The rule also has an obvious blind spot: vertical avoidance is only "back away when both sides fire", so a fly cannot choose to climb over an obstacle. Section Where to go next discusses what would be needed to change that. Mistakes found along the way These are real problems that came up during the project, kept here because they explain several design decisions. 1. pip refused to install (Arch Linux) error: externally-managed-environment. The system Python is protected. Fixed with a virtual environment. See Setting up Python. 2. The first cell-type search printed nothing The first inspection script ran to the end but its "candidate cell types" list was empty. I first suspected it had run out of memory. That was wrong: the newer pandas stores text as a dedicated str dtype, and my check looked for object columns, so it skipped every text column. The fix was to select the columns by name (type, superclass) instead of by dtype. The packaged 02_inspect_schema.py already does this. 3. An overstatement about LC6 I said I was confident LC6 drives the giant fiber. Later checking of the literature showed LC6 is looming-responsive and evokes takeoff, but is reported not to be a direct giant-fiber input. Corrected in Choosing the cells, with a script to check it in the data. 4. A shuffle control that did not shuffle the structure The first version of the control permuted the weights among the connections that already existed. Since which neurons connect to which is exactly what carries left/right structure, the fly still lateralised correctly and even hit less often than the intact one. It was not a control. It was replaced by rewiring: each connection keeps its source and strength but gets another connection's target. That produced the expected ordering (intact better than rewired better than no brain). 5. Floor clutter made the intact fly worse than no brain Obstacles originally bounced and rolled after landing. In 90 s of rain the intact fly was hit 14 times against 8 for the brain-cut fly. Tracing the hits showed 33 of the 54 total came from balls lying or rolling on the floor: the retreat rule sent the fly downward into them, and, most likely, the floor lies largely outside the eye fields (I inferred this from the geometry, not from a separate experiment). Making obstacles burst on first contact fixed it (intact: 1 hit in 90 s). 6. Too many head-on hits, then a knob that flatters everything With decisiveness 4, all 23 hits (out of 112 drops) were drops within 10 units of straight overhead (10 at offset 0 and 13 at offset −10 in the test grid): both eyes were stimulated almost equally and the sidestep was weak. At 10 only 3 hits remain (1 and 2 at the same offsets). It also made the rewired control look better (see Results), so it is a slider rather than a hidden constant. 7. Small tooling slips A shell brace-expansion ({a,b,c}) did not work in /bin/sh and created a literal folder; corrected by running under bash. Nothing in the deliverables depends on it. Still open: elevation from real data The 12.7 GB syn-points table holds synapse positions. As I understand it, the looming detectors' dendrites are arranged retinotopically in the optic lobe, so synapse positions could in principle give each neuron an approximate look direction. I have not checked that the table supports this, and the mapping would be approximate. That is feasible in a browser only with a compact binary file, and reading syn-points would need batch reading rather than loading it into pandas. Replace the single motor rule with roles for individual descending neurons taken from published function. Project log How the project unfolded, in order. Sizing the download. The dataset page lists seven tables totalling about 24.1 GB, plus skeletons, a database and image volumes that are not sized. The EM volume shape implies about a petabyte uncompressed (my arithmetic). The idea. A game in which a blue dot at the bottom dodges obstacles that fall when the user clicks, steered by the male connectome. I explained that the full connectome cannot run in a web page, so the plan became a small subset: sensors, relays and descending neurons, with the real weights. Choosing the files. Only 1.2 GB of the 24 GB was needed: annotations, neurotransmitters and weights. The three files downloaded fine. Setting up Python. pip refused on Arch; a virtual environment fixed it. First look at the tables. Schemas and sample rows appeared. The weights table has 151,856,684 rows. The cell-type search returned nothing because of the pandas string-dtype issue; fixed by selecting columns by name. Confirming the cell types. Counts for LPLC2 (185), LC4 (126), LPLC1 (134), LC6 (124) and the descending-neuron classes confirmed the plan was feasible. Building the circuit. The export script ran on the real data, producing 88 nodes and 482 edges and the report reproduced in this documentation. The report showed same-side direct wiring, mixed two-step wiring, and LPLC4 as the top relay. Designing the game around the data. Because only left/right is in the data, the earlier idea of four movement groups was dropped in favour of the left/right, back-away and homing rule. Testing and repairing. A stand-in circuit built from the report numbers exposed a broken control, floor clutter and a head-on weakness (all in Mistakes found along the way). The page was tested headlessly and published as a hosted page. Discussing 3D. Concluded that memory is not the limit and that elevation from data would need the synapse-position tables. This package. Documentation, scripts, tests, examples and the game bundled for offline use. While preparing it I checked the literature, which led to the LC6 correction and the caveat on the direction rule; and I reproduced the export script from the project record and re-ran it on synthetic data. Building the 3D version. Free-flight physics and full-3D sensing, reusing the same Brain class unchanged. A stand-in circuit test run again exposed real problems before anything was published: a naive test scenario that reported 0% hits in every condition (a flawed test, not a game bug — fixed by testing against continuous rain instead of staged single drops). Adding the real fly model. The user supplied fly.rar, a 1999 digitized insect model. Extracting it needed a proper unrar (the free one couldn't handle its solid-archive compression). The model's orientation wasn't stated anywhere in the file, so I rendered orthographic wireframes of the raw geometry to work it out before placing it in the scene. Parsed, centred, scaled and embedded as base64 so the published page needs no external files. Camera and room styling. Added a Chase/Free camera toggle (arrow keys plus click-drag for the free camera) and repainted the room to match the surrounding page's background instead of a dark, unrelated navy. A stale-object-reference bug in the camera tests themselves (see Testing the 3D version) was caught and fixed before publishing. This update.
